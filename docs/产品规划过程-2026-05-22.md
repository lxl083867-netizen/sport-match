# SportMatch 产品规划过程记录

**日期**: 2026-05-22 ~ 2026-06-20

---

## 心流轨迹与决策记录

### 起点：审视现状，规划方向

**用户思考**：网站核心功能已建成——认证、画像、视频库、反馈、推荐引擎、训练计划社区都有了。但感觉还不够深入，接下来该做什么？

**分析输出**：审查了全部 11 个页面和核心组件后，提出 5 个优先级建议：
1. 深色模式 —— DESIGN.md 明确规定了翻转变量的规则，运动场景夜间使用频繁
2. 计划详情页互动按钮 —— 点赞/收藏的 API 和数据库字段都已就绪，但页面缺少可操作的按钮
3. 移动端适配 —— DESIGN.md 定义了完整的响应式断点和 49px Tab Bar 规范
4. Python AI 评论分析管道跑通 —— 产品核心差异化能力，脚本已写完但未用真实数据验证
5. 计划"跟练"模式 —— 从"看到"到"做到"的闭环

**用户决策**：先做 1（深色模式），改动小、效果明显，顺手彻底验证 CSS 变量体系。

---

### 阶段 1：深色模式

**用户思考**：运动场景用户大概率夜间使用，深色模式体验断崖最明显。

**实施方案**：
- 方案选择：手动切换 + 系统偏好回退，localStorage 持久化，用 `data-theme` 属性控制而非纯 CSS media query
- 组件拆解：ThemeProvider（Context 状态管理）+ ThemeToggle（日/月双图标）+ 布局层注入阻塞脚本消除首帧闪烁
- 变量收敛：21 个 CSS 变量在 `[data-theme="dark"]` 下重新赋值，所有组件零改动——因为全部使用 `var(--color-*)` 引用

**关键决策**：不在组件中写 dark mode 特殊样式，完全依赖 CSS 变量层。这是 DESIGN.md 设计系统的核心价值——变量体系建立后，主题切换是 O(1) 的变量重赋值。

---

### 阶段 2：计划跟练模式

**用户思考**：现在计划只是一个视频清单。要做成"开始跟练 → 自动播放 → 每个完成打卡 → 全部结束总结"的完整闭环。

**实施方案**：
- 全屏沉浸式跟练界面 `PlanWorkout`，包含：进度条 + 计时器、嵌入视频播放（B站 iframe）、视频列表（已完成/当前/待完成三种状态）
- "完成并继续"按钮 → 调打卡 API → 自动步进到下一个视频
- 全部完成后弹出总结页：完成视频数、总时长、实际用时、逐项清单
- 非 B站视频（小红书/抖音）显示缩略图 + 外链引导

**关键决策**：不做成页内小组件，而是全屏覆盖层。跟练是专注场景，需要排除导航干扰。

---

### 阶段 3：互动按钮改进

**用户思考**：计划详情页的互动按钮不够好——有 emoji（违反 DESIGN.md §10 反模式）、没有选中态反馈、跟练按钮只是计数没有实际功能。

**实施方案**：
- 将 emoji 替换为 SVG 图标（心形/星形/播放三角）
- 点赞按钮：已赞状态下填充 + brand 蓝高亮
- 收藏按钮：已收藏状态下填充 + 橙色调高亮
- 新增 GET 端点返回用户互动状态，页面加载时同步
- "跟练"按钮重新定位为主 CTA——brand 蓝填充 + 播放图标，点击启动跟练模式

**关键决策**：DESIGN.md §10 规定"emoji 不出现在产品文案中"——这是规范落地的具体体现。互动按钮同时解决审美合规 + 交互反馈两个问题。

---

### 阶段 4：移动端适配

**用户思考**：用户大概率在手机上刷运动视频。目前桌面端 OK，但移动端缺少底部导航，布局也未针对小屏优化。

**实施方案**：
- 新建 `MobileTabBar`：49px 高度 + safe-area-inset-bottom 安全区，5 个标签（首页/发现/计划/推荐/我的），SVG 图标填充态区分选中
- NavBar 响应式：桌面端保留完整导航链接，移动端（<768px）隐藏，仅保留 Logo 和主题切换
- `<main>` 增加底部 padding 防止内容被 Tab Bar 遮挡
- `viewport` 导出配置 themeColor 用于浏览器顶栏着色
- 已有页面响应式网格审查通过（`grid-cols-1 md:grid-cols-2 lg:grid-cols-3` 模式一致）

**关键决策**：Tab Bar 仅在 `<1024px` 显示，而非 `<768px`——考虑到平板横屏场景，1024px 是更合理的桌面/移动分界线。DESIGN.md §7 定义了 1024px 为 Wide 断点起点。

## 今日技术决策总览

| 决策 | 选择 | 原因 |
|------|------|------|
| 主题切换方式 | `data-theme` 属性 + localStorage | 手动覆盖系统偏好，persist 跨会话 |
| 反闪烁策略 | `<head>` 阻塞脚本 + suppressHydrationWarning | 在首帧绘制前完成变量赋值 |
| 跟练模式形态 | 全屏覆盖层 | 专注场景不应有导航干扰 |
| 互动按钮图标 | SVG 内联 | 符合 DESIGN.md §10 反模式禁 emoji |
| 移动端导航 | 底部 Tab Bar（49px + 安全区） | 符合 DESIGN.md §8 Tab Bar 规范 |
| 断点策略 | 1024px 为桌面/移动分界 | 覆盖平板横屏场景 |

## 2026-05-25

### 阶段 5：首页信息架构重构

**用户思考**：首页"为你推荐/热门推荐/今日推荐"三个 tab 让人困惑，区别不清晰。首页应该按"视频推荐"和"训练计划"两个维度来划分。

**实施方案**：
- HomeTabs 从 3 个 tab 精简为 2 个（为你推荐/热门推荐），移除"今日推荐"tab
- 未登录用户只显示"热门推荐"，tab 切换器替换为副标题"按社区打卡热度排序"
- 热门计划卡片独立成一行展示在推荐视频下方
- 移除 `generateDailyPlan` 和 `todayPicks` 逻辑
- 首页最终布局：Hero/Welcome → 推荐视频(HomeTabs) → 最近练过 → 热门计划 → 画像提示 → 价值主张 → Footer

**关键决策**：未登录用户不展示 tab 切换器，避免给出一个大部分内容为空的操作入口。

### 阶段 6：计划广场排序修复

**用户发现**：在"我的"tab 点热门/最新排序没有反应——排序链接只带 `?sort=hot` 不带 `tab=mine`，导致切换排序时 tab 被重置为默认"推荐"。

**修复**：排序链接改为 `?sort=hot&tab=${tab}`，保留当前 tab 状态。

**另一个发现**：自己创建的计划在"推荐"和"全部计划"中完全不出现——因为 `hotPlans` 和 `otherPlans` 用 `!myIds.has(p.id)` 排除了自己的计划。

**修复**：移除排除逻辑，自己的计划也进入公开推荐池。

---

### 阶段 7：视频播放次数

**用户需求**：计划中某些视频需要多次锻炼（比如一组动作做 3 遍），默认每个视频一次，但应可设置次数。

**实施方案**：
- **Schema**: PlanItem 新增 `repeatCount Int @default(1)` 字段（1-99）
- **创建计划**: 每个视频行增加 `× N` 数字输入框
- **计划详情**: 次数 >1 时显示 `×3` 徽章，创建者可内联修改
- **跟练模式**: 次数 >1 的视频自动展开为多个连续步骤，进度条和列表显示"第 2/3 次"
- **总结页**: 完成视频数按展开后总步骤算，计划时长 = 视频时长 × 次数累加
- 新增 `PATCH /api/plans/[id]/items/[itemId]` 用于编辑次数和备注

**关键决策**：在跟练模式中把重复播放展开为独立步骤（而非原地循环），这样进度条、打卡、列表状态都是统一的一维流。

---

### 阶段 8：视频排序

**用户需求**：创建计划时视频顺序应该能调整，支持拖动或置顶。

**实施方案**：
- 每个视频行增加三个按钮：⤒ 置顶、▲ 上移、▼ 下移
- 复用已有 `order` 字段，序号实时重排

**关键决策**：用按钮而非拖拽实现——目前计划视频数量通常不多（<10个），按钮操作比拖拽更精准，且无需引入拖拽库或复杂的触摸事件处理。

---

### 阶段 9：视频缩略图与播放标签优化（前一阶段收尾）

**用户反馈**：视频卡没有预览封面，看着很空；跳转外部的提示太不显眼。

**实施方案**：
- `VideoThumbnail` 重写：支持真实缩略图（`thumbnailUrl`），加载失败时回退到平台色系几何占位图
- 播放标签从灰色小字改为醒目 pill 徽章：外部平台橙色 + 外链图标，B站绿色

---

### 阶段 10：SSR 重构（消除"加载中..."）

**用户发现**：视频浏览页和计划广场页首次加载时显示"加载中..."，体验差。

**实施方案**：
- `/videos` 和 `/plans` 从客户端组件改为服务端组件，直接 Prisma 查询渲染
- 筛选状态（搜索、平台、标签、排序）由 URL searchParams 驱动，点击筛选 = 导航到新 URL → 触发服务端重渲染
- 抽离 `VideoFilters.tsx` 和 `PlansToolbar.tsx` 作为纯交互层（"use client"）

**关键决策**：牺牲 SPA 式的无刷新切换，换取首屏零 loading 体验。运动场景用户通常是快速浏览决策，首屏速度优先于客户端路由过渡。

### 阶段 11：视频信息编辑

**用户发现**：自动抓取的小红书视频标题/作者名不准确，需要一个"修改信息"按钮。

**实施方案**：
- 新增 `PATCH /api/videos/[id]`，仅作者可编辑 title/sourceAuthor
- `EditVideoModal`：Apple 风格弹窗，修改后调用 PATCH + router.refresh() 刷新页面数据

## 今日技术决策总览

| 决策 | 选择 | 原因 |
|------|------|------|
| 首页 tab 结构 | 2 个 tab + 计划独立行 | 视频和计划是不同维度的内容，不应混在 tab 里 |
| 未登录排序显示 | 隐藏 tab 切换器，显示副标题 | 避免空状态操作入口 |
| 计划可见性 | 自己的计划也进公开池 | 默认公开，社区内容不应自我排除 |
| 视频重复播放 | Schema 字段 + 跟练展开为独立步骤 | 一维流管理统一，比循环嵌套简单 |
| 视频排序 | 置顶/上移/下移按钮 | 当前规模按钮比拖拽更精准，零依赖 |
| 列表页加载 | SSR 直出，URL 参数驱动筛选 | 首屏速度优先于客户端过渡动画 |
| 缩略图失败回退 | 平台色系几何图形 | 保持视觉识别度，不依赖外部图片可用性 |

### 阶段 12：计划广场精简

**用户思考**：当前计划页结构太复杂——先选"推荐"tab，再在"全部计划"区域点热门/最新排序，层级太多。用户要的就是 我的 / 热门 / 最新 三个视图直接切换。

**实施方案**：
- PlansToolbar 改为三个 tab：我的（仅登录可见）、热门（按点赞数降序）、最新（按创建时间降序）
- 移除"推荐"tab 和"全部计划"区域及其排序按钮
- 页面结构：标题 + Tab 切换 + 单一计划网格
- URL 参数精简为 `?tab=hot|new|mine`，移除 sort 参数
- 未登录用户只显示热门/最新，访问 mine 时提示登录

**关键决策**：将"排序"升格为"tab 视图"——热门和最新本身是不同的排序逻辑，用 tab 承载比用排序按钮更直观。

### 阶段 13：产品方向反思与收敛

**外部反馈（一针见血）**：

> 不是伪需求，但现在的解法很容易做成伪产品。真实需求是"我收藏了很多运动内容，但没人帮我筛、排、提醒、记录、复盘"。跨平台统一播放不是核心痛点——用户会问"我为什么不直接在原 App 收藏？"

**自检结论**：

当前产品有偏离核心价值的倾向。回顾近期开发工作：
- 缩略图优化、播放标签、跨平台外链、视频库浏览 —— 强化的是"视频管理工具"
- 推荐引擎、画像匹配、反馈闭环 —— 才是真正的差异化能力
- 前者投入多，后者投入少

**一句话定位修正**：

| | 旧 | 新 |
|---|---|---|
| 定位 | 跨平台运动内容策展引擎 | 帮你把收藏夹里的运动视频，变成今天能完成的训练 |

**调整方向**：

1. **强化推荐理由** —— "为什么推荐这个"比推荐本身更显眼。每条推荐附带 2-3 句中文理由（"匹配你的减脂目标"、"评论区多人反馈膝盖友好"）
2. **每日训练计划生成** —— 不是让用户自己拼计划，而是系统自动给出"今天练这 3 个视频"
3. **反馈闭环驱动优化** —— 练完打勾/反馈难度 → 下次推荐更准，这是留存引擎
4. **弱化** —— 视频库浏览的入口比重、"跨平台播放"的话术和功能比重

**优先级重排**：

| 优先级 | 模块 | 原因 |
|--------|------|------|
| P0 | 每日推荐生成（AI 排计划） | 核心价值——"今天练什么" |
| P0 | 推荐理由展示 | 差异化感知——"为什么是这个" |
| P1 | 反馈闭环（练后记录 → 优化） | 留存引擎 |
| P1 | 画像引导（身体条件/禁忌） | 安全感和信任 |
| P2 | 训练计划 UGC | 社区飞轮 |
| P3 | 视频库浏览 | 辅助入口，不是主入口 |
| P3 | 跨平台播放优化 | 够用就行，不深挖 |

**二次打磨（收藏意图 vs 全网推荐）**：

> 系统根据画像用全网视频拼今日计划 — 这句是危险的。用户收藏过的视频暴露了他的真实运动意图，这才是最独特的资产。改成纯画像+全网推荐会变成普通运动推荐 App。

**修正后的核心逻辑**：

| 层 | 用户状态 | 首页给什么 |
|----|---------|-----------|
| 零门槛 | 新用户 | 3 个问题（想练什么/多久/身体限制）→ 即刻生成今日训练 |
| 收藏增强 | 用过一次 | 提示"导入收藏后会更懂你"，用户已体验到价值 |
| 长期个性化 | 有收藏有画像 | 优先从收藏生成训练，缺热身/拉伸/安全替代时用推荐补齐 |

**关键原则**：收藏不是门槛，是加速器。没收藏也能生成"今天练什么"，有收藏就生成"更像你自己想练的"。

**首页三种状态**：

1. **未登录/新用户** → 主 CTA：生成今天训练 + 副 CTA：稍后导入收藏
2. **已登录但没收藏** → 主卡片：基于画像的今日训练 + 提示"添加收藏后会更懂你"
3. **已登录有收藏** → 主卡片：基于收藏意图的今日训练（来源：最近收藏的 X 个视频，已补齐热身/拉伸）

**收藏诊断显性化**（首页第二屏）：
- 你最近收藏最多的是：臀腿、拉伸、低冲击
- 你偏好的训练时长：15-30 分钟
- 你收藏里缺少：热身
- 有几个视频可能对膝盖压力较高

这比单纯的"推荐理由"更有杀伤力——用户会觉得：它真的读懂了你的收藏夹。

**实施方案** (2026-05-26)：

- 新建 `TodayPlanCard.tsx`：首页登录后的主卡片，替代原来的简单欢迎语
- 三种状态：无画像 → CTA 设置画像 | 有画像无收藏 → 推荐驱动方案 | 有画像有收藏 → 收藏优先方案
- 收藏优先逻辑：从用户视频中按 phase 标签（热身/主训练/拉伸）分类，画像匹配打分排序，缺环节时用推荐补齐
- 收藏诊断卡片：展示最关注的标签方向、偏好时长、缺失环节、风险警告
- 价值主张文案同步更新（未登录页的三列说明改为"今日训练方案/收藏意图诊断/反馈持续优化"）

### 阶段 14：零门槛冷启动（QuickStart）

**用户反馈**：策略讨论中提出的三层递进——第一层"新用户回答 3 个问题即刻出方案"还没实现。当前登录无画像用户只看到一个 CTA 跳转到完整 profile wizard。

**实施方案**：
- 新建 `QuickStartCard.tsx`：登录无画像时首页直接展示，不用跳转到 `/profile/setup`
- 3 个问题分步展示，带进度条：想练什么 → 有多久 → 身体限制
- 每步可选跳过，最终提交调用 `/api/profile`（upsert 模式填写默认值）
- 提交后 `router.refresh()` 触发服务端重渲染，即刻看到今日训练方案
- 完整画像设置（器材、禁忌等）仍保留在 `/profile/setup` 作为进阶选项

**关键决策**：3 个问题即可生成方案，不是 6 步 wizard。剩余的细粒度画像（器材、禁忌动作等）是"增强信号"而非"准入门槛"。

### 阶段 15：推荐理由显性化 + 练后反馈

**推荐理由显性化**：

每个视频下面展示两类理由：
- **为什么选它**：标签匹配生成的中文短句（"匹配减脂目标"、"适合零基础"、"可用瑜伽垫"）
- **为什么排在这里**：热身→"热身激活，为后续训练做准备"、主训练→"核心训练，匹配你的目标强度"、拉伸→"冷身拉伸，帮助恢复"

理由在 page.tsx 服务端生成（`getReasons` 函数），匹配画像标签后输出 `matchReasons` + `phaseReason`，TodayPlanCard 在每个视频行下方以 chip 形式展示。

**练后反馈闭环**：

PlanWorkout 总结页新增两组快速反馈按钮：
- **难度**：太简单 / 刚好 / 太难 → 调用 `/api/feedback`（difficultyRating）
- **推荐**：下次还想练 / 不太想 → 调用 `/api/feedback`（recommend）

每个视频独立提交，非阻塞。提交后显示"反馈已记录，下次训练会更适合你"。推荐引擎的 `getRecommendations` 已有对应的反馈信号处理（太难→降权高强度视频、不想练→降权同类视频），现在从反馈到推荐形成了闭环。

### 阶段 17：推荐算法分层（收藏意图相似度）

**用户需求**：推荐算法应分层——收藏优先，同意图相似其次，补齐结构再次，热门兜底。第 2 层"与收藏意图相似的视频"此前缺失。

**实施方案**：
- `lib/recommendation.ts` 新增 `getCollectionTagProfile()`：从用户收藏视频中提取高频标签作为"意图向量"（排除热身/拉伸等阶段标签，取 top 10）
- `getRecommendations` 新增 `collectionProfile` 参数：候选视频与收藏意图标签匹配时加分
  - goal/muscle/type 类标签匹配 +7（高权重，代表"练什么"）
  - duration/equipment 类标签匹配 +4（辅助权重）
  - 匹配时追加理由"与你收藏的「XXX」类型相似"
- `app/page.tsx`：有收藏时从已加载的 `userVideos` 中计算 `collectionProfile`，传入所有 `getRecommendations` 调用（补齐缺口 + 发现页推荐）

**四层推荐现状**：

| 层 | 描述 | 实现方式 |
|---|---|---|
| 1. 用户收藏视频 | 从收藏中按 phase 分类，画像匹配打分排序 | page.tsx 直接分类+评分 |
| 2. 与收藏意图相似 | 补齐时优先找与收藏高频标签相似的视频 | `collectionProfile` → `getRecommendations` |
| 3. 补齐训练结构 | 缺热身/拉伸时用推荐补齐 | phase 过滤 + 推荐结果填充 |
| 4. 热门视频 | 发现页兜底 | `HomeTabs` 热门 tab（独立于今日计划） |

**关键决策**：收藏意图权重低于画像匹配（7 vs 10），确保"适合你"优先于"像你收藏的"。不会因为收藏了大量瑜伽视频就推荐不适合你身体条件的瑜伽内容。

### 阶段 18：每日计划不污染"我的"计划列表

**关键决策**：每日计划仍保留在 DB 中（可通过首页卡片点击查看详情），但不会出现在任何计划列表中。`isDaily` 字段比用标题匹配更可靠、可维护。

### 阶段 19：练后反馈分开提交

**用户反馈**：跟练完成后选了一项反馈（难度或推荐），整个反馈区就关闭了——应该两项都能独立选择。

### 阶段 20：首页临时方案 + 手动加入"我的"

**关键决策**：浏览不写库，用户主动保存才落库。保存过的计划是用户的真实资产，不会被系统自动覆盖。开关式交互比二次确认弹窗更轻量、更流畅。

### 阶段 28：推荐算法 — "换一个"分层排除

**契机**：移动端测试账号只导入了 2 个视频，点"换一个"没有反应——`pick()` 函数从高分候选中随机洗牌，但素材太少时仍抽到同一批视频，用户感知不到变化。

**用户洞察**：用户收藏不够时，应优先换库补的视频（热身/拉伸/额外主训练），收藏的主训练尽量不动。只有前两次都没换出新鲜感时，第三次才把收藏也换掉。

**实施方案**：
- `pick()` (lib/today-plan.ts) 新增可选 `excludeIds?: string[]`，排除项推到候选池末尾后再随机洗牌
- `generateTodayPlan()` 接受 `options.currentVideoIds` + `options.refreshCount`，按策略计算实际排除列表
- 分层策略：refreshCount 0 或 1 → 只排除库补视频 ID（收藏不动）；refreshCount ≥ 2 → 排除全部当前方案视频 ID（收藏也换）
- `generateTodayPlan()` 中也用 `userVideoIds` Set 区分收藏 vs 库补，排除时判断视频归属
- 首次生成（app/page.tsx）不传 options，无排除，正常生成

**关键决策**：换一个不是无脑刷新，而是"先换辅助、再动核心"的分层体验。即使用户只有 2 个收藏，第一次换也能看到库补视频的变化。

### 阶段 29：计划编辑 + 被收藏锁定

**契机**：用户提出"我的"计划应提供可编辑的入口，但如果被他人收藏了就不能修改（只能删除）。

**实施方案**：
- 新增 `PATCH /api/plans/[id]` — 编辑计划标题 + 描述 + 视频列表，`favoritesCount > 0` 时拒绝编辑返回 403
- `app/plans/[id]/page.tsx` 新增编辑模式：拥有者可见"编辑计划"按钮，被收藏后显示灰色禁用文字，hover 提示原因
- 编辑模式下：标题变 input、描述变 textarea、视频项出现 ↑↓ 排序 + ✕ 移除 + 次数输入框
- "删除计划"按钮始终可用（删除不受收藏限制）
- 首页移除热门计划板块，底部 Tab Bar 顺序调整为 首页 → 计划 → 发现 → 我的
- 视频次数显示优化：浏览模式下始终显示"重复 N 次"（含 1 次），编辑模式下才可修改

**关键决策**：修改和删除是两个不同权限层级。被收藏后编辑锁死但删除放行——创作者对自己发布的内容拥有最终处置权。

### 阶段 30：Video 所有权拆分 — 从"谁的视频"到"谁收藏了它"

**契机**：导师指出"Video 到底属于谁"是当前最大的数据模型风险。`Video.userId` 既是"谁导入的"又是"谁拥有它"——A 删了自己的视频，B 的计划里就出现"视频已失效"。更关键的是，用户引用别人的视频加入自己计划，正是产品乐于看到的推荐网络效应。

**实施方案**：
- 新增 `UserVideo` 模型（`@@unique([userId, videoId])`）——用户收藏关系独立于全局视频
- 数据迁移：6 个已存在 `Video.userId` 全部回填为 `UserVideo` 记录
- `DELETE /api/videos/[id]` → 改为只删 `UserVideo`（"从收藏中移除"），不再物理删除 Video
- `POST /api/videos` → 导入时同时创建 `UserVideo`；URL 已存在 → upsert `UserVideo`（多人共享同一 Video）
- `PATCH /api/videos/[id]` → 只允许原始导入者（`Video.userId`）编辑全局信息；`EditVideoButton` 用 `isOriginalImporter` 而非 `isImported` 判断
- 全站"我的视频"查询（page.tsx、daily-plan/refresh、profile、recommendation.ts、videos/page.tsx mine tab）全部改为通过 `UserVideo` 查询
- API 返回新增 `isImported`（当前用户是否已导入）+ `importCount`（多少人导入）
- 组件命名：`isOwner` → `isImported`（语义正确）

**关键决策**：`Video` 是公共资源，`UserVideo` 才是"我的收藏"。删除操作变成"从收藏中移除"而非"删除视频"。这打开了隐性的网络效应——用户 A 的精选收藏 → 推荐给画像相似的用户 B → B 加入计划 → A 和 B 都受益。Video.userId 保留为 deprecated，向后兼容。

### 阶段 32：工程化第一阶段 — 统一错误处理

**契机**：此前讨论"从原型到成熟产品的差距"时，指出 catch 块大量静默吞错误——用户点按钮没反应，不知道发生了什么。这是最高频、最痛的问题。讨论敲定了五阶段渐进式工程化路线后，本周从第一阶段开始。

- 新建 `components/Toast.tsx`：Toast 通知系统，三种类型（error/success/info），5 秒自动消失，toast() 函数通过 Context 全局可用
- `app/layout.tsx` 包裹 `<ToastProvider>`
- 全站 13 个文件的 17 个用户主动触发的 mutation 操作全部替换为 `api()` + toast：
  - 导入视频、从收藏移除、编辑视频信息
  - 刷新今日方案、加入/移除我的计划
  - 提交反馈（详情页 + 跟练总结页）
  - 跟练打卡（CheckInButton + PlanWorkout）
  - 保存画像（ProfileEditor + QuickStartCard + ProfileWizard）
  - 注册
  - 创建计划、编辑计划、删除计划、计划互动
- 每个操作都有 loading 态、成功 toast、失败 toast，保留原业务逻辑不变
- 仅覆盖 mutation（写操作），查询类 fetch 保持不变

**关键决策**：不一次性替换全站 fetch，只改用户主动触发的写操作。这是回报率最高的一步——不需要改业务逻辑，只改调用层，但任何 API 报错用户都能看到具体原因，不再是静默失败。

### 阶段 35：PlanWorkout 恢复逻辑产品化讨论

**契机**：手动验收中发现反馈接口报错（`completionRate` 默认值 `100` 与 `String` 类型不匹配），更关键的是：用户在讨论中提出了一个核心体验问题——"返回"可能是误触，进度恢复应该是默认行为，而非只有"刷新页面"这种意外场景才恢复。

**产品思考**：

> "如果用户返回了页面再点进来（很容易误触），也应该恢复上次的训练进度，除非用户再次进来时手动表达了要重新跟练这个计划，才重置。"
>
> "用户昨天练完今天打开还是总结页，这种体验很不好。应该在退出后一段时间自动重置为一个新的计时状态。"

**最终方案**：

| 场景 | 行为 |
|------|------|
| 跟练中途退出（← 退出 / 总结返回 / 刷新 / 页面关闭）再进来 | 恢复到第一个未完成步骤，正常继续 |
| 全部完成后再进来 | 直接显示总结页 |
| 想重练 | 点"重置训练" → 确认弹窗 → 从第 1 项开始 |
| 退出后超过 1 小时 | session 自动过期，下次进来是全新状态 |
| 不同计划之间 | 互不串（planFingerprint 唯一标识） |

**关键设计决策**：

1. **"返回计划"不再清除进度** —— 从总结页返回后，session 保留。用户明天打开看到的是上次的总结，或者超过 1 小时自动清零。

2. **1 小时自动过期** —— 最初设为 2 小时，经讨论后降到 1 小时。连续多天训练同一计划的用户，每次打开都会感觉到"这是一个新的训练"，不会被历史进度困扰。

3. **"重置训练"需要主动操作** —— 两个入口：跟练顶部按钮（低需求，与"退出"同字号同颜色）+ 总结页与"返回计划"并排按钮（高频需求，独立实心按钮）。所有入口都弹出确认弹窗防误触。

4. **反馈 API 修复** —— `completionRate` 在 Schema 中定义为 `String`（`"fully"/"partial"/"abandoned"`），但 batch API 默认值写成了数字 `100`，导致永远写入失败。改为 `"fully"`。

5. **完成反馈动画** —— "完成此项" / "完成训练" 点击后按钮变绿色 + 显示"已完成 ✓" + 微微放大，停留 0.6 秒后自动前进。给用户一瞬的成就感确认，而不是机械地秒跳到下一项。最后一项同样处理，0.6 秒后进入总结页。

**改动文件**：`components/PlanWorkout.tsx`（唯一文件，大量修改）、`app/api/feedback/batch/route.ts`（一行 fix）

**后续微调**：
- React Strict Mode 导致恢复 toast 弹两次 → `didRestoreToast` ref 确保只弹一次
- 总结页点"重置训练"无反应 → 确认弹窗挪到 `if (showSummary)` 之前，两个视图共用
- 跟练顶部"重置训练"样式：`text-[14px] text-white/50` 与"退出"统一；总结页"重置训练"改为与"返回计划"并排的实心按钮

**产品洞察**：

> "对已完成训练的重置需求是高频率的（用户要重复做同一个计划），应该跟'返回计划'同等权重，平行放置。而在未完成的训练过程中，重置是低频需求，放在顶栏就够了。"

这体现了从功能实现到体验分层的过程——不同场景下的同一操作，权重不同，呈现就该不同。

**后续微调**：
- React Strict Mode 导致恢复 toast 弹两次 → `didRestoreToast` ref 确保只弹一次
- 总结页点"重置训练"无反应 → 确认弹窗共用，两个视图均有效
- 跟练顶部"重置训练"样式与"退出"统一；总结页"重置训练"改为与"返回计划"并排的实心按钮

### 阶段 38：反馈闭环 — 从"记录了"到"学会了"

**契机**：之前的反馈只是写入数据库，但没有反向影响下一次推荐。"点过太难/不喜欢"和"下次方案变了"之间没有可感知的因果。这是"训练后调整下一次方案"的关键一环。

**实施方案**：
- `lib/today-plan.ts` — 新增三个核心函数：
  - `getFeedbackSignals(userId)` — 从 `UserFeedback` 表提取四个维度的信号：困难标签计数、不喜欢标签计数、喜欢的视频 ID、近期趋势（太简单/太难）
  - `scoreVideo()` — 反馈信号接入评分引擎：
    - 太难标签 × 置信度 → -4 至 -12
    - 不喜欢标签 × 置信度 → -6 至 -18
    - 明确 dislike 的视频 → -80（直接排除）
    - 膝盖/腰部不适反馈 → -28
    - 喜欢标签 → +4
    - 近期太难 → 降高强度 +12，升低强度 +5
  - `getFeedbackHash(userId)` — 反馈数据摘要，变化后触发自动方案刷新
- `TODAY_PLAN_VERSION` 加入 profile hash 计算，反馈变化 → hash 变化 → 自动重新生成方案（不计入 3 次）
- `explanation.items` 新增 `"feedback"` tone（黄色 pill），显示"根据上次反馈，今天降低了 X 训练难度"
- `generateTodayPlan()` 返回值新增 `feedbackAdjustment?: string`，首页可显示一句话调整说明

**完整闭环链路**：
```
完成跟练 → 点"太难"/"不想练" → 写入 UserFeedback
    → 第二天打开首页 → getFeedbackHash() 变化
    → 自动重新生成方案（刷新次数不变）
    → 方案解释卡展示黄色 feedback pill："根据上次反馈调整"
    → 下次方案真的变了
```

**关键决策**：反馈闭环不是"所有代码跑通了"就行，关键是**用户要感知到变化**。"feedback" tone 的黄色 pill 就是这层感知。不做复杂的 ML 模型，纯规则加权，可解释、可调试。

## 下一步优先级（阶段性总结）

截至 06-20，SportMatch 的核心闭环（画像→方案→跟练→反馈→洞察）已比较完整。工程化路线的 5 个阶段完成了 3 个（错误处理、五态覆盖、接口加固）+ 4 个产品阶段（洞察卡、解释卡、反馈闭环、UI统一）。下文是几个候选方向及判断。

### 1. 次日感知（P0 — 最小成本最大留存杠杆）

用户在计划完成总结页返回后，第二天打开应该看到"你已经连续训练了 N 天"或"上次你完成了核心训练，今天已根据反馈调整了强度"的感知信号。不需要做复杂的 streak 系统，一行文字就能建立"系统在记住我"的印象。这是留存引擎的第一步。

### 2. B站收藏夹同步（P0 — 撬动内容供给侧）

手动粘贴链接是产品当前最大的用户摩擦力。B站用户的运动收藏夹里可能有几十个视频，但被"依次粘贴"的操作门槛劝退。B站有公开 API 可拉取用户收藏列表并按分区筛选运动类，技术上可行。做成"从 B站同步收藏"一个按钮，一步替代手动导入流程。

### 3. 内容质量白名单（P1 — 防止推荐池污染）

不对导入视频做任何质量判断是当前的系统性风险——用户可能导入 vlog、MV、纯知识讲解类视频，一旦进入推荐池会影响所有人。至少加一道导入时的分区/标签白名单检查：非运动类弹确认窗 "这可能不是运动教程，确认导入？"。不需要 LLM，纯规则。

### 4. 抽 Service 层（P2 — 工程债务）

几轮迭代之后，一些 API route 已经超过 100 行。业务逻辑和鉴权/校验代码混在一起。抽离不会立刻带来新功能，但会显著降低后续改代码的调试成本。
